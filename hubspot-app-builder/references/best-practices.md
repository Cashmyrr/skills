# HubSpot App Best Practices

Rules to apply on **every** HubSpot developer-platform project (2026.09). Each rule says what to do, why, and what the mistake looks like. When a rule conflicts with a quick fix, the rule wins.

Sources are the official HubSpot docs linked at the bottom. Items marked *(Cashmyrr convention)* are team conventions, not HubSpot requirements.

---

## 1. Project & versioning

- **Pin `platformVersion` to the Current version** (`"2026.09"`) in `hsproject.json`. Never start a new project on a Supported or Sunset version.
- **Pin dependency versions** in every `package.json` (cards, pages, settings, functions). `"latest"` makes two builds of the same commit behave differently.

  ```json
  // ❌ Avoid
  "@hubspot/ui-extensions": "latest"
  // ✅ Do — pin the version you tested, upgrade deliberately
  "@hubspot/ui-extensions": "1.0.1"
  ```
  Check the current version with `npm view @hubspot/ui-extensions version` before starting, and read the release notes before bumping a major (1.0.0 shipped in November 2026).
- **Commit `package-lock.json`** and the files generated by `hs project lint` (ESLint config + devDependencies).
- **One project = one Git repository**, deployed from CI (see [`validation.md`](validation.md)), never from a developer laptop to production.
- **Keep the CLI current**: `npm install -g @hubspot/cli@latest` before starting a session (profiles need CLI 8.x, configurable test accounts need 8.3.0+).

## 2. Environments (dev / QA / prod)

- **Use build profiles** instead of hardcoding account-specific values. Create one profile per environment, each pointing to a **different account**:

  ```shell
  hs project profile add dev  --target-account <dev-test-account-id>
  hs project profile add qa   --target-account <qa-test-account-id>
  hs project profile add prod --target-account <prod-account-id>
  ```

  This creates `src/hsprofile.<name>.json`:

  ```json
  { "accountId": 1234567, "variables": { "API_BASE_URL": "https://api-qa.example.com" } }
  ```

  Reference variables in any `*-hsmeta.json` as `${API_BASE_URL}` (e.g. `redirectUrls`, `permittedUrls`, `name`) and in UI extensions via `context.variables.API_BASE_URL`.
- **Every profile must define every variable** used in the project, or the upload fails.
- Once a project has profiles, **every** `hs project upload|dev|deploy` needs `-p <profile>`. That is a feature: it makes the target explicit.
- **Develop and test in developer test accounts**, never in the client's production portal. Create them reproducibly from a config file committed to the repo:

  ```shell
  hs test-account create-config                    # generates a config file
  hs test-account create --config-path ./test-accounts/qa.json
  hs test-account import-data --account <id> --file-path ./test-accounts/seed.json
  ```

  Set the hub tiers in the config (e.g. `"salesLevel": "ENTERPRISE"`) to match what the client actually has. Testing on an Enterprise trial when the client is on Professional hides missing-feature bugs.

## 3. Auth, scopes & secrets

- **Least privilege**: request only the scopes the code actually calls. Put "nice to have" scopes in `optionalScopes`, never in `requiredScopes`. Each extra required scope is a reason for an admin to refuse the install and a reason for the Marketplace review to reject.
- **Never put a secret in front-end code** (cards, pages, settings). React code ships to the browser. Secrets live in:
  - serverless function secrets (`hs secret add <NAME>`, declared in `secretKeys`, read with `process.env.NAME`), or
  - your own backend, called through `hubspot.fetch()`.
- **Never commit a token**: no `pat-…`, private-app token, client secret or API key in the repo, in `hsprofile.*.json` variables, or in examples. Profile variables are not secrets.
- **Validate `X-HubSpot-Signature-v3`** on every backend endpoint that receives webhooks or `hubspot.fetch()` calls. See [`signature-validation.md`](signature-validation.md).
- **Prefer user-level access (2026.09)** when the app acts on behalf of a user and must respect that user's HubSpot permissions — see the User-Level Access section of `SKILL.md` for constraints (no serverless functions, no app cards).
- **OAuth tokens**: refresh based on `expires_in`, not on receiving a `401`.

## 4. Calling HubSpot APIs (rate limits)

Current limits (usage guidelines page):

| App type | Burst limit | Daily limit |
|---|---|---|
| Marketplace (OAuth) app | 110 requests / 10 s **per installing account** (CRM Search excluded) | — |
| Private app, Free/Starter | 100 / 10 s | 250,000 / day (shared by the account) |
| Private app, Professional | 190 / 10 s | 625,000 / day |
| Private app, Enterprise | 190 / 10 s | 1,000,000 / day |

CRM Search, Associations and GraphQL have **separate, lower** limits. Marketplace apps must keep error responses **under 5 %** of their daily requests.

Rules:
- **Use batch endpoints** (`/batch/read`, `/batch/create`, `/batch/update`, `/batch/upsert`) instead of loops of single calls.
- **Use webhooks instead of polling** for change detection.
- **Cache** data that does not change per request (owners, pipelines, property definitions).
- **Paginate** with the `after` cursor; never assume one page contains everything.
- **Throttle client-side** to stay under the 10-second burst limit, and read the `X-HubSpot-RateLimit-Max` / `-Remaining` / `-Interval-Milliseconds` headers.
- **On `429`**: retry with exponential backoff + jitter, with a maximum number of attempts *(Cashmyrr convention — HubSpot does not prescribe an algorithm)*. Never retry immediately in a tight loop.
- **Use date-based API versions** (`/YYYY-MM/` paths) for new code; legacy `v3`/`v4` paths still work but certified apps must use a supported date-based version.

## 5. UI extensions (cards, pages, settings)

- **Every data-driven view handles four states**: loading, error, empty, success. Use `LoadingSpinner`, `ErrorState`/`Alert`, `EmptyState`.

  ```tsx
  // ❌ Avoid — error is ignored, card renders "undefined"
  const { properties, isLoading } = useCrmProperties(["email"]);
  if (isLoading) return <LoadingSpinner />;
  return <Text>{properties.email}</Text>;

  // ✅ Do
  const { properties, isLoading, error, refetch } = useCrmProperties(["email"]);
  if (isLoading) return <LoadingSpinner label="Loading contact…" />;
  if (error) return <ErrorState title="Couldn't load the contact"><Button onClick={refetch}>Retry</Button></ErrorState>;
  if (!properties.email) return <EmptyState title="No email on this contact" />;
  return <Text>{properties.email}</Text>;
  ```
- **Use the SDK hooks** (`useExtensionApi`, `useCrmProperties`, `useAssociations`) rather than the legacy `fetchProperties` action, and type them with the location generic (`useExtensionApi<'crm.record.tab'>()`).
- **Call hooks at component level**, never inside handlers, loops or conditions.
- **Use `hubspot.fetch()`**, never browser `fetch()`. `body` is a plain object — no `JSON.stringify()`, no manual `Content-Type`. Only the `Authorization` header can be customized. URLs must be in `permittedUrls.fetch`.
- **Encode user/CRM data in URLs**: `encodeURIComponent(properties.email)`. Better: send it in the POST body.
- **Respect `hubspot.fetch()` limits**: 20 concurrent requests, 15 s timeout, 1 MB payload. Set an explicit `timeout`. Don't fire one request per row — aggregate on your backend.
- **One primary button per surface**; destructive actions use destructive styling and a confirmation (modal). Use `LoadingButton` for async actions to prevent double submission.
- **Use HubSpot components only** — no attempts to inject custom HTML/CSS. Keep text short, use `Text variant="microcopy"` for secondary info.
- **Use `logger`** (`logger.info|warn|error`) for anything you need to see in production logs; remove `console.log` debugging before merge. Logs are rate-limited (1,000/min per account) — don't log in render loops.
- **Never display sensitive data** (sensitive-data scopes, payment data, health data) in cards.

## 6. Serverless functions

- **Async/await only**; no callbacks.
- **Return a predictable shape** and **never return the raw error object** — it can leak request headers or tokens to the front end *(Cashmyrr convention for the shape)*:

  ```js
  // ❌ Avoid
  } catch (err) { console.error(err); return err; }

  // ✅ Do
  } catch (err) {
    console.error("getContacts failed", err.code || err.message);
    return { ok: false, error: { message: "Could not load contacts", status: err.code || 500 } };
  }
  ```
- **Keep functions small and fast**: one responsibility per function, no long-running jobs (use your own backend/queue for those).
- **Remember the plan requirements**: private app functions need Enterprise (or a developer test account); public endpoint functions need Content Hub Enterprise and are not available in test accounts. Serverless functions are not supported in user-level apps.

## 7. Webhooks

- **Validate the signature first**, then respond `200` fast and process asynchronously (queue). HubSpot retries failed deliveries, so slow handlers create duplicates.
- **Make handlers idempotent**: deduplicate on `eventId` — the same event can be delivered more than once and out of order.
- **Subscribe only to the events you handle**, and to the properties you need (`propertyChange` on specific properties, not everything).

## 8. Deploy & rollback

- **Upload to a test/QA profile first**, install there, test, then deploy to prod.
- **Know your rollback before you deploy**: `hs project list-builds --project <name>` then `hs project deploy --build <id> -p prod` redeploys a previous good build.
- New projects **auto-deploy** after a successful build. Use `hs project upload --skip-auto-deploy` when you want to build without deploying, or disable auto-deploy in the project Settings for prod.

## 9. Things to never do

- Hardcode a portal ID, account ID, owner ID, pipeline ID or stage ID — read them from context, settings, or profile variables.
- Develop directly against a client's production portal.
- Request `requiredScopes` "just in case".
- Store or log secrets, tokens or full CRM payloads containing personal data.
- Ship with `"latest"` dependencies, `console.log` debugging, or TODOs in error paths.
- Declare a task done without going through [`validation.md`](validation.md).
